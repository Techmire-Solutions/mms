## 2. Protocol Version Inspection (HTTP/1.1, HTTP/2, HTTP/3)

### Current Live Deployment Audit (`tms.mmsv2.aabtaab.com`)

Direct network probe via ALPN negotiation:

```bash
node -e "
const https = require('https');
const options = { hostname: 'tms.mmsv2.aabtaab.com', port: 443, path: '/contacts', method: 'GET' };
const req = https.request(options, (res) => {
  console.log('ALPN Protocol:', res.socket.alpnProtocol);
  console.log('HTTP Version:', res.httpVersion);
});
req.end();
"
# Result:
# ALPN Protocol: false
# HTTP Version: 1.1
```

### Analysis of the 6,900 ms Lighthouse Opportunity

- **Observation:** The live host terminates TLS at an Apache 2.4.58 reverse proxy (`Server: Apache/2.4.58 (Ubuntu)`).
- **Finding:** ALPN is currently returning `false` (negotiating HTTP/1.1), causing browsers to open multiple parallel TCP connections (up to 6 per domain) rather than multiplexing all sub-resource requests (JS chunks, CSS, webfonts) over a single HTTP/2 multiplexed stream.
- **Root Cause in Infrastructure:**
  In `/etc/apache2/sites-available/mmsv2.conf`:
  - `Protocols h2 http/1.1` is missing from the `<VirtualHost *:443>` block, and/or Apache module `mod_http2` (`a2enmod http2`) is not explicitly active with MPM event.
- **Server Configuration Upgrade Required on Production Host (Ops):**
  ```apache
  <VirtualHost *:443>
      ServerName mmsv2.example.com
      ServerAlias *.mmsv2.example.com

      # Enable HTTP/2 multiplexing alongside HTTP/1.1 fallback
      Protocols h2 http/1.1
      H2Direct on

      SSLEngine on
      ...
  </VirtualHost>
  ```
  _Note:_ In accordance with MMS deployment rules, server-level Apache changes require an SSH ops maintenance window with configuration backup (`cp /etc/apache2/sites-available/mmsv2.conf /etc/apache2/sites-available/mmsv2.conf.bak`).

## 3. Server Response Headers & Caching Strategy

Live inspection of production responses across all asset classes:

### A. Fingerprinted Static Assets (`/assets/*.js`, `/assets/*.css`)

```http
HTTP/1.1 200 OK
Server: Apache/2.4.58 (Ubuntu)
Cache-Control: public, max-age=31536000, immutable
Vary: Accept-Encoding
ETag: W/"26d4-1a1af76a618-br"
Content-Type: application/javascript; charset=utf-8
Content-Encoding: br
```

- **Evaluation:** **Exemplary.**
- Assets generated by Vite contain 8-character cryptographic hashes in their filenames.
- Fastify's `staticAssets.ts` applies `Cache-Control: public, max-age=31536000, immutable`. Browsers never revalidate these assets on repeat visits, eliminating 100% of static asset latency.

### B. Application Shell Entry (`/contacts` / `index.html`)

```http
HTTP/1.1 200 OK
Server: Apache/2.4.58 (Ubuntu)
Cache-Control: no-cache, no-store, must-revalidate
Pragma: no-cache
Vary: Accept-Encoding
Content-Type: text/html; charset=utf-8
Content-Encoding: br
```

- **Evaluation:** **Exemplary.**
- Ensures the HTML entry point is never cached stale by intermediary proxies or browsers, allowing immediate rollout of new deployment hashes without stale chunk loading errors.

### C. Authenticated Contacts API & Personal Records (`/api/contacts`)

```http
HTTP/1.1 200 OK
Cache-Control: private, no-cache, no-store, must-revalidate
Vary: Accept-Encoding, X-Tenant-Id, Authorization
Content-Type: application/json; charset=utf-8
Content-Encoding: br
```

- **Security & Multi-Tenancy Compliance:**
  - Guaranteed: **Zero public caching** for contact identities, phone numbers, addresses, or personal records.
  - Intermediary caches (CDNs, edge proxies, shared browsers) cannot cache or leak tenant data across organizations due to `private, no-cache, no-store, must-revalidate` and `Vary: Accept-Encoding, X-Tenant-Id, Authorization`.
  - Conditional caching with tenant-scoped SHA-1 ETags (`W/"<tenant>-<hash>"`) ensures instant 304 Not Modified responses when data has not changed, saving client bandwidth without privacy risk.

## 4. Compression Verification (Brotli vs Gzip)

### Production Asset Responses:

1. **Static Bundle Assets (`.js`, `.css`):**
   - Served with `Content-Encoding: br`.
   - Pre-compressed during build time using `vite-plugin-compression2` with Brotli quality 11 (`constants.BROTLI_PARAM_QUALITY: 11`).
   - Disk artifacts: `index-[hash].js.br` and `index-[hash].css.br` are served directly by `@fastify/static` with zero CPU overhead on the backend.
2. **Dynamic API Payloads (`/api/contacts`):**
   - Served with `Content-Encoding: br` or `gzip` depending on client `Accept-Encoding`.
   - Compressed on-the-fly via `@fastify/compress` (Brotli quality 4 for optimal latency-to-compression ratio, threshold 1024 bytes).

## 5. Resource Waterfall & Duplicate Request Elimination

### Initial Contacts Load Waterfall:

1. `GET /contacts` (HTML shell, ~3.6 kB, Brotli-compressed).
2. Parallel fetch of critical JS & CSS (`index-[hash].js`, `index-[hash].css`).
3. Non-blocking Google Fonts preload (`fonts.googleapis.com` / `fonts.gstatic.com`).
4. `GET /api/contacts?page=1&limit=50` (Primary table data).
5. Dynamic chunks loaded only on demand:
   - Modals (`ContactForm`, `DuplicateDetection`, `ContactsImportDialog`, `MessageComposer`) are lazy-loaded via `React.lazy()` and `Suspense`.
   - Secondary link data waterfalls (`useContactsDirectoryLinks.ts`) are gated behind drawer activation (`hasActiveOverlay`), preventing background link resolution on clean list views.
